■ 概要
PCをActive Directoryドメインに参加させます。

■ 設定ファイル
[domain.csv]
  Enabled     : 有効フラグ（1=実行, 0=スキップ）
  domain      : ドメイン名（例: example.local）
  user        : ドメイン参加用アカウント
  pass        : パスワード（ENC: プレフィックス付き暗号化文字列も利用可）
  dns         : DNS サーバの IP アドレス（接続確認に使用）
  ou          : コンピュータオブジェクトの作成先 OU（省略可）
                完全な識別名（DN）で指定します。空欄の場合はドメイン既定の
                コンテナ（通常 CN=Computers / redircmp で変更可）に作成されます。
  Description : 説明（表示用）
  Segment     : Segment フィルタ（省略可）

[記載例]
  Enabled,domain,user,pass,dns,ou,Description,Segment
  1,example.local,Administrator,P@ssword123,192.168.1.1,"OU=Kitting,OU=PC,DC=example,DC=local",本番ドメイン,

  ※ DN はカンマを含むため、ou 列は必ずダブルクォートで囲んでください。
     囲み忘れると値が途中で切れますが、その場合は DN 形式チェックが
     Error で止めるため、意図しない OU に参加することはありません。
  ※ 拠点別・機種別に OU を出し分けたい場合は Segment 列を使います
     （行ごとに ou と Segment を組み合わせる）。

[入れ子になった OU の書き方]
  DN は「深い方から浅い方へ」書きます。左端が実際に入れる OU で、
  右へ行くほど上位です。

    example.local
    └─ OU=PC
       └─ OU=Kitting
          └─ OU=Tokyo

    PC に入れる      : "OU=PC,DC=example,DC=local"
    Kitting に入れる : "OU=Kitting,OU=PC,DC=example,DC=local"
    Tokyo に入れる   : "OU=Tokyo,OU=Kitting,OU=PC,DC=example,DC=local"

  ・途中の OU は省略できません（飛ばすと存在しないパス扱いで status 0x2）
  ・末尾の DC= はドメイン FQDN をドットで割ったものです
    （example.local → DC=example,DC=local）
  ・いちばん多い間違いは順序の逆転です。OU=PC,OU=Kitting,... と上位から
    書くと存在しないパスになり status 0x2 で失敗します（誤った OU に
    入ることはありませんが、原因が分かりにくいので注意）
  ・OU 名自体にカンマを含む場合は OU=Sales\,EMEA とエスケープします

  顧客 AD では DN を推測せず、実物をコピーするのが確実です。
    ADUC → 表示 → 拡張機能 をオンにする → 対象 OU のプロパティ →
    属性エディター タブ → distinguishedName の値をコピー
    （RSAT があれば Get-ADOrganizationalUnit -Filter "Name -eq 'Kitting'" |
      Select-Object DistinguishedName でも取れます）

■ 前提条件
・管理者権限が必要です（Add-Computer の実行）
・DNS サーバへのネットワーク接続が必要です
・ENC: パスワードを使う場合は Fabriq 起動時のマスターパスフレーズ入力が必要
・ou を指定する場合、その OU が AD 上に既に**存在している**必要があります
  （参加処理は OU を作りません）
・OU へのコンピュータオブジェクト作成は、次のどちらかで通ります（実測 2026-09-13）
    (a) その OU に「コンピュータオブジェクトの作成」を委任されたアカウント
        → 作成数は無制限。オブジェクトの所有者は作成したアカウント
    (b) 委任なしの一般ドメインユーザー（既定で Authenticated Users が持つ
        「ドメインへのワークステーションの追加」権利）
        → ms-DS-MachineAccountQuota（既定 10）**までは OU 指定でも作成可能**。
          オブジェクトの所有者は Domain Admins になる
  つまり「委任が無いと OU 指定できない」わけではありません。ただし (b) は
  アカウントごとのクォータで頭打ちになるため、長く使い回す参加用アカウントは
  ある日突然作れなくなります（その場合は (a) の委任に切り替えてください）
・委任は OU 単位です。ou を空欄にして既定コンテナ（CN=Computers）へ参加させると、
  委任を持っているアカウントでも (b) の権利経路に落ち、クォータを消費します
  （実測 2026-09-13: 同一アカウントで、委任済み OU へ作ったオブジェクトには
  mS-DS-CreatorSID が付かず、既定コンテナへ作ったオブジェクトには付いた）。
  参加用アカウントを使い回す運用では、ou を指定して委任済み OU へ入れる方が
  安全です

■ 注意事項
・参加失敗時は即座に Error ステータスで返却します（無限リトライしません）
・リトライ・スキップ・ダイアログ表示の制御は profile CSV の
  ErrorMode 列および FlexProfile dashboard に委譲します
・DNS サーバが Ping 不到達の場合、Add-Computer を試みずに即 Error 返却します
  （診断メッセージ "DNS unreachable: <ip>" が dashboard に表示されます）
・ou は「コンピュータアカウントを新規作成するとき」にのみ効きます。
  既に参加済みの PC で ou を書き換えて再実行しても冪等性チェックで Skip され、
  オブジェクトは移動しません（既存オブジェクトの移動は AD 側の作業です）
  また、AD に同名オブジェクトが残っている状態で ou を指定した場合、その
  オブジェクトが指定した OU 以外にあると参加そのものが失敗します
  （status 0x8b0。移動はされません → 下記「■ 再キッティング」）

■ 再キッティング（AD に同名オブジェクトが残っている場合）※実測 2026-09-13

既存オブジェクトの再利用には、独立した関門を順に通す必要があります。

  関門0: 指定した OU と、既存オブジェクトが実際に居る OU の一致
         （ou を指定したときだけ）
    通過条件 = 既存オブジェクトが、ou に書いた OU の直下に「既にある」こと
    失敗時   = netsetup.log status 0x8b0（「アカウントは既に存在します」）
    ※ 参加 API が要求 DN と実在 DN を突き合わせて弾きます。長さで先に比較し、
       長さが同じ場合は文字列で比較します（どちらの経路も実測で確認）。
       オブジェクトが指定 OU へ移動することはありません。
    ※ 対処は 3 つ: 旧オブジェクトを削除する / ou を実際にある OU に合わせる /
       ou を空欄にする（ou を指定しなければ、今ある場所のまま再利用されます）

  関門1: 再利用ポリシー（KB5020276）
    通過条件 = 参加に使うアカウントが「そのオブジェクトを作成した本人」、
               または「管理者が作成したオブジェクト」であること
    失敗時   = netsetup.log status 0xaac
    ※ 参加に使うアカウントが Domain Admins でも免除されません。
       効くのは「誰が作ったか」だけです（実測で確認）

  関門2: オブジェクトへの書き込み権（ACL）
    通過条件 = パスワードのリセット / dNSHostName・SPN の検証済み書き込み /
               アカウント制限の書き込み が可能であること
               （オブジェクトの所有者は暗黙に保持しています）
    失敗時   = netsetup.log status 0x5（アクセス拒否）
    ※「コンピュータオブジェクトの作成」の委任だけでは通りません。
       これは新規作成の権限であって、既存オブジェクトの更新権限ではありません

したがって、同じ PC 名で作り直す運用では次のいずれかを選びます。

  (1) 毎回、AD 側で古いコンピュータオブジェクトを削除してから参加する（確実）
  (2) 前回と同じ参加用アカウントを使い続ける
  (3) 顧客 AD 側で参加用アカウントに「ドメイン参加の委任一式」を付けてもらう
      （作成 + 削除 + パスワードリセット + dNSHostName / SPN の検証済み書き込み +
       アカウント制限の書き込み）。この場合、管理者が作成したオブジェクトは
      そのまま再利用できます
・ou には OU=... しか指定できません。CN=Computers のようなコンテナを指定した場合は
  Add-Computer を呼ぶ前に Error で停止します
  （参加 API 側が "Specified path '<dn>' is not an OU" として status 0x2 で必ず失敗する
  ことを Windows Server 2025 + Windows 11 で実測済み。既定コンテナに入れたい場合は
  ou を空欄にしてください）
・参加後の再起動では、サインイン先の既定がドメインになります。ローカルアカウントで
  ログオンするには「.\ユーザー名」または「コンピュータ名\ユーザー名」と入力してください
  （ユーザー名だけだとドメインアカウントとして認証され、失敗が重なると
  Windows 11 の既定ロックアウトポリシー（10 回 / 10 分）でロックされます）
・自動ログオン（autologon_config / Windows Update ループ）をローカルアカウントに
  設定している場合、ドメイン参加後は DefaultDomainName が実態と合わなくなり
  自動ログオンが成立しないことがあります。ドメイン参加と改名を伴うプロファイルで
  __RESTART__ を跨ぐ場合は、再開時に手動ログオンが必要になる前提で組んでください
・参加に失敗した場合、確認すべき点のチェックリストと
  C:\Windows\Debug\netsetup.log の status コードを表示します
  （Add-Computer のエラー本文は OS 言語により日本語化されるため、
  言語非依存の status コードを併記しています）

■ 改名を伴う参加（hostname_config と同じ実行で参加する場合）
hostname_config の改名は再起動まで保留されます。間に __RESTART__ を挟まずに
本モジュールが走ると、AD には「改名前の名前」でコンピュータオブジェクトが
作られ、再起動後にマシン名と AD 上のアカウント名が食い違って、納品前から
信頼関係が壊れた状態になります。

これを避けるため、本モジュールは保留中の改名を検出すると、自動的に
「改名後の名前」で参加します
（Add-Computer -Options AccountCreate,JoinWithNewName）。
プレビューの Computer 行に「旧名 -> 新名 (staged rename)」と表示されます。

・__RESTART__ を正しく挟んであるプロファイルでは保留改名が存在しないため、
  この分岐には入りません（従来どおりの動作）
・AD に作られるオブジェクトは改名後の名前になります。ou と併用できます

【再起動前の見た目の食い違いに注意】※実測 2026-09-13
JoinWithNewName 付きの参加は、保留中の改名を「確定」まで進めます。そのため
参加が終わった時点で、ipconfig /all のホスト名も GUI の改名ダイアログも
新しい名前になります（改名の保留状態は解除されます）。

一方 %COMPUTERNAME% だけは起動時に撮られたスナップショット
（ActiveComputerName）なので、再起動するまで旧名のままです。

  ipconfig /all のホスト名    → 新名
  GUI の改名ダイアログ        → 新名
  %COMPUTERNAME% / fabriq SELF → 旧名（再起動まで）

つまり同じ実行の中で domain_join より後ろにあるモジュールは、旧名を
見続けます。エビデンスやチェックリストに記録されるホスト名も旧名です。
改名と参加を含むプロファイルでは、domain_join の後ろに __RESTART__ を
置いてください。

■ 動作の流れ
1. domain.csv から有効なエントリを読み込み
2. 参加済み判定（同一ドメインなら Skip / 別ドメインなら Error）
3. ou 指定時は DN 形式を検証（不正なら Add-Computer を呼ばずに即 Error）
4. 保留中の改名を検出（あれば改名後の名前で参加する）
5. 設定内容（computer / domain / account / dns / ou）をプレビュー表示
6. DNS サーバへの Ping 接続を 2 回プローブ（不到達なら即 Error）
7. ドメイン参加を実行（成功なら Success、Add-Computer 例外なら即 Error + 診断表示）
8. 参加後の検証（ドメインメンバーシップ。OU 配置は検証しません → 下記）

■ AutoPilot / FlexProfile
AutoPilot モードでは確認をスキップして CSV の設定を自動適用します。
失敗時の挙動は profile CSV の ErrorMode 列で宣言してください。

  ErrorMode=retry : 失敗時に最大 5 回まで自動再試行（DNS 復旧待ち等の
                    一過性障害向け、kernel 既定 AutoPilotMaxRetry=5）
  ErrorMode=skip  : 失敗をログに残して次モジュールへ自動継続
  ErrorMode=空白  : Show-AutoPilotErrorDialog で operator が
                    Retry/Skip を意思決定

FlexProfile では失敗しても dashboard に戻り、Status バッジで Error が
視認できるため、[Run] ボタンで domain_join のみ単発再試行することも可能です。

■ Post-Apply Verification
本モジュールは Post-Apply Verification を実装しています。検証しているのは
「ドメインメンバーシップ」のみです。

Add-Computer 成功直後に Win32_ComputerSystem を読み返し、PartOfDomain が真かつ
Domain が CSV の domain と一致するかを検証して New-ModuleResult に -Verified
（$true/$false）を渡します（実行履歴の Verified 列に記録）。ドメイン参加は再起動を
待たずに Win32_ComputerSystem へ即時反映されるため（再起動は参加の完了のみ）、
適用直後でも検証が成立します。

■ OU 配置を検証しない理由 ※実測 2026-09-13

ou を指定した場合でも、コンピュータオブジェクトが実際にどの OU に入ったかは
読み返していません。「まだ作っていない」のではなく、「検証しても意味がない」と
判断したためです。

参加 API 自身が OU を検証していて、食い違えば必ず失敗するからです。

  ・指定した OU が存在しない / OU でない            → status 0x2 で失敗
  ・同名オブジェクトが別の OU にある                → status 0x8b0 で失敗
    （要求 DN と実在 DN を突き合わせて弾く。長さ比較 → 文字列比較の 2 段）
  ・同名オブジェクトが同じ OU にある                → その場で再利用
  ・同名オブジェクトが無い                          → 指定 OU に新規作成

つまり「参加が成功したのに別の OU に居る」という結末が存在しません。ここで
ディレクトリを読み返しても、返ってくる答えは常に「一致」です。
**落ちることのない検証は検証ではありません。**そのために LDAP 依存を 1 つ
抱えるのは割に合わないと判断し、実装しない選択をしました。

成功時は「Requested OU: ...（enforced by the join API, not re-read here）」と
情報表示するにとどめます。

逆に言うと、OU に関する問題は必ず「参加の失敗」として現れます。そのため
投資先は検証ではなく診断側に置いてあり、失敗時は netsetup.log の status コードと
対処方法を表示します（特に 0x8b0 は Windows のメッセージが「アカウントは既に
存在します」としか言わず、真因である OU 不一致が分からないため、明示的に
補足しています）。
